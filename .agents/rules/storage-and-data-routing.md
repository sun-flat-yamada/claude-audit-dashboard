# Storage & Data Routing Rules

## Fork-Safe Architecture

This project is designed to be **forked** by downstream enterprise organizations.
The `main` branch of upstream (`sun-flat-yamada/claude-audit-dashboard`) must contain **zero live data**.

### Branch Strategy

```
main              ← Code and the synthetic sample only. No audit data. Fork-safe.
data/audit        ← Orphan branch. Audit snapshots, reports and state (per fork)
```

### Why Orphan Branch?

1. **Fork Isolation** — When a downstream fork runs `Sync Fork`, only `main` code is synced. Audit data stays local to each fork.
2. **History Separation** — Audit data commits don't pollute code history or inflate repository size.
3. **Access Control** — Branch protection rules can restrict who writes to the data branch.
4. **Clean Upstream** — Upstream `main` is always clean, ready for `Sync Fork` with zero conflicts.
5. **Long-term Retention** — Data persists independently of code releases.

### Initialization

All reads and writes of the branch go through `.github/scripts/data-branch.sh`:

```bash
.github/scripts/data-branch.sh restore            # copy data/ from data/audit (no-op before the first run)
.github/scripts/data-branch.sh save "<message>"   # mirror data/ to data/audit and push
```

The first successful `save` creates the orphan branch. `save` refuses to run without a prior `restore` in the same checkout (it mirrors deletions, e.g. archived snapshots), never copies `data/sample/`, and is serialized by the `audit-data` concurrency group shared by every writing workflow.

### Branch protection (fork-safety)

- **No saving from a public repository**: `save` exits non-zero with `::error::` when `REPOSITORY_VISIBILITY` is `public` (or any value other than `private` / `internal`). Every writing workflow (`collect-audit.yml`, `weekly-report.yml`, `monthly-report.yml`, `ack-alert.yml`, `ledger-backfill.yml`, `ledger-seal.yml`, `ledger-verify.yml`) passes `REPOSITORY_VISIBILITY: ${{ github.event.repository.visibility }}` and `GH_TOKEN: ${{ github.token }}` to its save step; inside GitHub Actions an empty value is resolved with `gh api repos/<owner>/<repo>` and the save fails closed when it stays unknown. Outside Actions an unset value is a local run (unchanged).
- **Deletion / force push**: protect `data/**` with a repository ruleset (restrict deletions, block force pushes); steps in `docs/DEPLOYMENT.md` (_Protecting the data branches_).
- **Fork of a fork**: a fork of a downstream fork must be created with _Copy the `main` branch only_, otherwise GitHub copies `data/audit` (live data) too.

### Dashboard Build Pipeline

`deploy-pages.yml`:

1. Checks out `main`
2. Stages `packages/dashboard/public/data/dashboard.json`: from `data/audit` when the repository variable `PAGES_DATA_SOURCE=live`, otherwise from `data/sample/`
3. Stages the per-person detail files `packages/dashboard/public/data/detail/` (including the effective configuration `detail/config.json`, the archive inventory `detail/archive.json`, the alert history `detail/alerts.json`, the time-point comparison files in `detail/compare/` and the monthly cost files in `detail/monthly/`): the sample's `data/sample/detail/` by default; with `PAGES_DATA_SOURCE=live` the `data/detail/` of `data/audit` **only if** the repository variable `PAGES_DETAIL_DATA=true` (explicit Private-Pages attestation, default off)
4. Builds with `STAGED_DATA=1` so `scripts/stage-data.mjs` keeps the staged file
5. Deploys to GitHub Pages

Locally, `pnpm dev` / `pnpm build:dashboard` stage `data/dashboard.json` when it exists (after `pnpm build:data`), else the sample. The SPA fetches `data/dashboard.json` relative to the Vite base path.

### Data Retention & Archival

- Raw snapshots: `retention.snapshotDays` (default 365), then `pnpm archive` moves them to `data/archive/<year>/` (gzip)
- Archiving shrinks the working tree, **not the git history**: the archived snapshots' blobs stay in `data/audit` and the `.json.gz` files are added. `pnpm size --repo . --ref data/audit` measures the history (`git count-objects -v`, reachable size, growth per 30 days, blobs per dataset) against `capacity.*` in `config/default.json`; the collect workflow runs it before the save, notifies through the usual channels (key `capacity:<level>`, cooldown applies) and never fails the collection because of it (`--warn-only`). Bound the size with the yearly orphan-branch rotation in `docs/DEPLOYMENT.md`.
- `pnpm cli restore <id|year> [--out <dir>]` writes `archive/<year>/<id>.json.gz` back to `snapshots/<id>/` (byte-identical, never overwriting); `pnpm build:data --snapshot <id>` / `pnpm build:detail --snapshot <id>` rebuild the dashboard and detail files from it.
- Monthly ledger: retained indefinitely. One file per month and dataset with merge rules per kind (`event` keeps the first copy per id, `daily` keeps the newest `asOf` per date + breakdown, `rollup` keeps the latest per month + id, `state` adds a version only when the content hash changes); a month with `sealed: true` in its `MANIFEST.json` is never rewritten (details: `docs/BLUEPRINT.md` §6.5)
- Compliance, weekly and monthly reports: retained indefinitely
- Archived data: retained indefinitely
- Anthropic Compliance API retains audit logs for 6 years, but this system stores independently for longer-term access

### fork:verify Script

The `pnpm fork:verify` script ensures:

1. No live data paths are tracked on the code branch (`FORBIDDEN_PATHS` in `scripts/fork-verify-paths.ts`, including `data/ledger/`)
2. `data/sample/dashboard.json` (and, when present, the gitignored `data/sample-optional-sources/` written by `pnpm demo --profile optional-sources`) matches the published `DashboardView` contract and has `source: "demo"`; `data/sample/detail/` matches the detail contract with masked identifiers and `example.*` e-mails only
3. `data/sample/` contains only `example.*` e-mail addresses
4. No secrets in tracked files; `.gitignore` excludes `.env`, `node_modules`, `dist`; `.env.example` holds no real values

### Ledger encryption at rest (#162)

Optional and off by default. Recipient private keys (`CADL-SECRET-...`) stay offline and are never stored in GitHub; the workflows read the encrypted ledger with the separate symmetric key `LEDGER_PIPELINE_KEY` (Actions secret). Key files (`pnpm ledger keygen`) and decrypted copies (`pnpm ledger decrypt`) are written only outside the data directory and the repository and never on CI, so they cannot reach `data/audit`, `main` or a workflow artifact. Encrypting does not rewrite history: plaintext versions committed earlier stay in `data/audit` until the yearly rotation (`docs/DEPLOYMENT.md`). Snapshots are not encrypted.

### External copies of sealed months (#161)

Optional and off by default (`ledger.sink: none`). `pnpm ledger push` (run by `ledger-seal.yml` after the seal, and by the seal itself through the `SealedMonthSink` hook) copies a **sealed** month of `data/ledger/` to `filesystem` (a directory outside the repository and the data directory, refused otherwise), `gdrive` (a Google Drive shared drive) or `sharepoint` (a SharePoint / OneDrive library). The copy holds the stored bytes (encrypted files stay encrypted) in the ledger's own layout (`<yyyy-mm>/<dataset>.jsonl.gz[.enc]`, `revisions/`, `MANIFEST.json` without `transfers`), so it can be restored by hand into `data/ledger/<yyyy-mm>/`. It is the same raw data as the ledger: the storage must be private to the organization, with a retention policy the organization sets (`docs/SETUP.md`). Nothing is copied from the main branch or from `data/sample/`, and the tools never delete in the copy. Credentials: GitHub OIDC federation only (no secret in GitHub); identifiers in repository variables.

### Alert acknowledgement (F-008)

`data/alerts/ack.json` (`ACK_STORE_SCHEMA_VERSION = 1`) is the acknowledgement store. It is separate from `state.json` (`parseState()` resets unknown shapes) and is **not** staged for Pages: the dashboard reads only the joined, redacted `detail/alerts.json`. It is written only by `pnpm alerts ack <alert-id> [--by <label>]` and the `Acknowledge Alert` workflow (`.github/workflows/ack-alert.yml`), which restores `data/audit`, records the acknowledgement, rebuilds `detail/alerts.json` and saves back to `data/audit` under the `audit-data` concurrency group, never to `main`. Anyone with repository write access can run that workflow. An unreadable `ack.json` is never overwritten.
